# Functional Teaching Gear — Product, UI/UX, and Technical Brief

**Status:** Implementation brief for the next dedicated feature task  
**Prepared:** 14 September 2026  
**Scope:** Phase-one Learn experience  
**Depends on:** the Production Learning Kernel and Persistent Learner State workstreams

## 1. Goal

Teaching Gear makes the tutor's teaching method controllable and observable.

The learner should be able to say, in effect: *give me the essential answer*, *teach me through it*, or *show me why it works*. They should also be able to adjust one specific part of a response without losing the lesson they were reading.

The feature is successful only when the selected control changes the **typed teaching plan** before generation. A shorter answer alone is not Quick; a longer answer alone is not Deep. Each control must have a defined instructional effect, an auditable plan field, a structured-output requirement, and automated examples that demonstrate the difference.

### Product outcome

For one objective and one learner state, the tutor can produce:

| Learner request | Product result |
|---|---|
| “Just give me the core idea.” | A compact, accurate explanation with only essential definitions and bridges. |
| “Teach me this.” | An intuitive explanation, a useful example, manageable steps, and an optional response opportunity. |
| “I want to understand why it works.” | The mechanism, assumptions, derivation where useful, boundary cases, and relevant connections. |
| “Make that simpler.” | The selected passage is re-expressed with less abstraction and smaller steps, while preserving meaning. |
| “Why is that true?” | The precise claim is justified; the lesson is not restarted from the top. |
| “Show me an example.” | A concrete, bounded example with stated assumptions and a checked result where the system can check it. |
| “Visualize it.” | A supported, labeled visual representation plus an equivalent text explanation, or an honest fallback. |
| “Check whether I understand.” | A small independent-response prompt with no answer leakage and no automatic mastery increase. |

## 2. Product boundaries

### In scope

- One persistent session-level setting: **Quick**, **Guided**, or **Deep**.
- Seven local response actions: **Simpler**, **Why?**, **Example**, **Visualize**, **Check understanding**, **Go deeper** (the local Deep expansion), and **Resume**.
- A profile resolver that combines the persistent gear and a single explicit local override into a typed plan.
- Main-chat and sidecar/selected-passage behavior that preserves the original lesson and its anchor.
- A bounded visual vocabulary: relationship diagram, comparison table, number line, worked structure, and validated plot when data/functions are supported.
- A small first-principles understanding check with independent-response protection.
- Persisted plan, profile, action ID, plan version, and action lifecycle so later state, branches, and evaluations can explain what happened.
- Backend and UI tests that compare paired plans and rendered blocks for the same objective.

### Explicitly out of scope

- A control for hidden model reasoning time, model tier, or token budget. This product control is about teaching, not exposing model internals.
- A complete assessment engine, grading engine, spaced-repetition product, or calibrated mastery algorithm.
- Arbitrary executable simulations or browser code generated by a model.
- A broad settings page, a permanent inferred learner personality, or automatic model switching based on guesses.
- Rewriting old lessons in place. Regeneration creates a later lesson artifact while the old one stays available for anchors and branches.

## 3. Current implementation audit

The repository already contains important foundations. This feature should extend them instead of introducing a parallel control system.

### Backend today

- `backend/app/session_models.py` defines `TeachingGear` (`Quick`, `Guided`, `Deep`) and typed intents for `teach`, `simplify`, `example`, `why`, `visualize`, `check_understanding`, and `resume`.
- `backend/app/policy_models.py` already defines `ResolvedTeachingProfile`, `ActionContext`, `TeachingPlan`, prerequisite outcomes, and policy validation results. The profile carries depth, abstraction, step size, derivation, example mode, response mode, a local override, and the current limited visual format.
- `backend/app/learning_kernel.py` resolves a free-form or explicit intent, creates structured lesson blocks from the plan, and does not create learner evidence while rendering a lesson.
- `backend/app/main.py` persists a plan, validation result, artifact, and action events before it completes a teaching action. The action endpoint supports state-version checks and an `Idempotency-Key`.
- `backend/app/model_provider.py` uses the plan and profile in its server-side structured-output prompt. A deterministic provider remains available for testability; optional provider configuration is server-side only.

### Web experience today

- The Learn screen uses a ChatGPT-like composer in `web/components/learn-chat.tsx` and calls `learningApi.createSession` plus `learningApi.teachingAction` in `web/lib/api.ts`.
- The newer chat path currently creates sessions with **Deep** hard-coded and sends every normal teaching action with **Deep** hard-coded. This is the first functional integration defect to resolve.
- The older map/lesson workspace has a visible `<Select>` for Quick, Guided, and Deep and local action buttons, but those local buttons are mostly client-side presentation switches. They must become real action commands.
- Passage selection already opens a non-modal study panel and can request `explain`, `simpler`, `example`, `symbols`, or `why`. This is the right interaction model for anchored local controls, but it needs one shared action contract.

### Implication

The kernel must remain the sole owner of teaching-profile resolution. The browser may remember the user’s chosen gear and request an explicit local action, but it must never infer plan semantics by hiding or adding paragraphs locally.

## 4. Teaching-profile contract

The persistent gear selects defaults. A local action modifies only the relevant dimensions for one action.

```text
session default gear
        +
explicit local action / selected passage anchor
        ↓
resolved teaching profile
        ↓
teaching plan
        ↓
structured lesson blocks + verification status
```

### 4.1 Persistent presets

| Dimension | Quick | Guided | Deep |
|---|---|---|---|
| Primary promise | Essential answer | Learn it step by step | Understand the mechanism |
| Explanation depth | Essential | Scaffolded | Mechanistic |
| Abstraction | Accessible | Balanced | Technical only where useful |
| Step size | Large | Manageable | Fine |
| Examples | Zero or one only if needed | One worked example when useful | More than one representation when useful |
| Prerequisites | Essential definitions/bridge only | One focused diagnostic or bridge where material | More thorough but bounded exploration |
| Derivation | Omit unless required for truth | Include when it helps | Include when appropriate and foundations permit |
| Connections | Only essential | Relevant to current goal | Meaningful, goal-aware connections |
| Response opportunity | Brief optional prompt | Guided optional prompt | Independent application/transfer prompt |

All presets preserve the same objective, trust/correctness floor, source policy, learner permissions, and assessment restrictions.

### 4.2 Local override semantics

| UI action | Typed intent | Changes | Does not change |
|---|---|---|---|
| Simpler | `simplify` | abstraction → accessible; step size → smaller; unfamiliar terms → defined inline | objective, correctness floor, session gear |
| Go deeper | `why` with an expansion anchor, or dedicated future `deepen` intent | mechanism/assumptions/derivation for one anchor | unrelated parts of the lesson |
| Why? | `why` | causal or logical justification of selected claim | selected concept unless the claim needs a short definition |
| Example | `example` | adds a concrete scenario, stated inputs and assumptions, and result boundary | original explanation’s position and scope |
| Visualize | `visualize` | selects a supported visual specification and equivalent text | visual fidelity or safety checks |
| Check understanding | `check_understanding` | creates an independent-response prompt and private evaluation metadata | mastery; it changes only after separate evidence admission |
| Resume | `resume` | restores session/branch position and recap | learner state or prior lesson content |

### 4.3 Precedence rules

1. Correctness, safety, permissions, source limitations, and assessment restrictions are mandatory.
2. The current objective and selected anchor remain fixed unless the learner explicitly chooses another concept.
3. An explicit local request overrides the matching presentation dimension for that one action.
4. The session’s selected gear supplies all remaining defaults.
5. A saved branch-local profile applies before the session default for that branch.
6. Inferred preferences are advisory only and may fill no required field. They must never silently change the saved gear.

This makes **Deep + Simpler** valid: it remains thorough and mechanism-oriented while explaining terms and notation gradually. It must never collapse into Quick.

## 5. UI/UX design

### 5.1 Design position

The interface should borrow the useful interaction principle behind ChatGPT’s mode picker: one compact choice near the point of composition, plain-language labels, an obvious current state, and no settings-page detour for an everyday decision. Forma uses the same compactness while making a different promise: **how the tutor will teach**. The learner must not be asked to understand model selection or reasoning effort.

The visual language stays aligned with the current product: quiet canvas, dark text, restrained borders, a single small spark/compass accent, and controls that become visible when they are useful. The gear is a learning tool, not a dashboard widget.

### 5.2 Primary control in the composer

Place a compact **Teach: Guided** button in the composer footer, beside attachment controls and before Send. It opens a small anchored menu; it is not a row of three permanent large buttons.

```text
┌───────────────────────────────────────────────────────────────┐
│ Ask anything, or drop in a book…                               │
│                                                                 │
│ [attach]  Teach: Guided ▾                          [send ↑]    │
└───────────────────────────────────────────────────────────────┘
```

The menu contains exactly three choices:

| Row | Label | Secondary line |
|---|---|---|
| 1 | Quick | The essential answer, with only needed definitions. |
| 2 | Guided | Intuition, a useful example, and manageable steps. |
| 3 | Deep | Mechanism, assumptions, and the reasoning underneath. |

Requirements:

- Use the existing `Select` or a `DropdownMenu`/radio-group composition rather than a custom inaccessible picker.
- The active row has a check mark and concise description; do not rely on color.
- Selecting an option closes the menu, changes the composer label immediately, and saves the **session preference** after a session exists. It does not mutate an in-flight request.
- On first use, default to Guided. Do not default the chat flow to Deep.
- A short tooltip explains: “Changes how the next answer is taught. It does not change what you are learning.”
- Do not include Auto in V1. Auto has hidden trade-offs in a learning product; the learner’s explicit choice is more important.

### 5.3 Lesson-header state and regeneration

Every assistant lesson has a small metadata row:

```text
Forma   ·   Guided   ·   Limited source support                     •••
```

Clicking **Guided** opens the same picker. Its menu contains a quiet divider and one explicit command:

```text
Apply Deep to this explanation
```

This creates a new action with the existing lesson as the parent and preserves the older response. It must be visibly described as a regeneration, not an instant rewrite. When the session gear changes from the header without choosing “Apply,” display a short non-blocking note: **“Deep will apply to your next response.”**

### 5.4 Local lesson actions

Below each rendered lesson, show a compact action strip. It should be context-aware rather than a permanent wall of controls.

```text
[ Simplify ] [ Why? ] [ Example ] [ Visualize ] [ Check understanding ]
```

- **Simplify**, **Why?**, and **Example** open an anchored response below the selected block when a block is selected; otherwise they use the most recent meaningful block.
- **Visualize** opens an inline visual block when the requested visual is safely supported. Otherwise the response says which visual forms are available and offers a comparison table or textual structure.
- **Check understanding** opens a focused check card beneath the lesson. It does not show a correct answer until an answer is submitted and evaluated by the later evidence workflow.
- **Go deeper** appears as the primary local command for a selected explanation or inside the study panel, instead of competing with the global Deep setting.
- Use disabled/loading states such as “Preparing example…” and “Building visual…”. Each state is tied to an action ID so a late result cannot insert itself into another lesson.

### 5.5 Selected passage and sidecar behavior

Selection remains the natural doorway for precise local help:

```text
Selected passage
  Explain · Simpler · Why? · Example · Symbols
```

The non-modal study panel retains the quoted anchor and lesson breadcrumb. A local response inherits the parent lesson’s resolved profile, then applies only its selected override. A sidecar should show a compact profile label such as **“Guided · simpler language”**, not a second session gear selector by default.

An explicit branch-level setting may be added later through a “More options” affordance. It must not unexpectedly change the main lesson.

### 5.6 Mobile and accessibility

- On narrow screens, the composer picker becomes a bottom sheet/radio list with the same labels and descriptions.
- The action strip wraps into two rows or an overflow menu; no control may be clipped horizontally.
- Every gear choice is keyboard reachable and announced as a radio selection.
- The study panel is a labeled non-modal region on desktop, preserving access to the lesson. On narrow screens, use a real modal sheet with correct focus trapping and a visible return action.
- A visual block includes alt-equivalent structured text and labels. Color is never the only way to understand it.
- The current gear, local override, trust state, and action progress must be accessible text, not icon-only status.

## 6. Backend implementation design

### 6.1 Keep one control resolver

Create or extend a focused policy function, for example:

```python
resolve_teaching_profile(
    session_gear: TeachingGear,
    intent: TeachingIntent,
    anchor: BranchAnchor | None,
    branch_override: BranchTeachingOverride | None,
) -> ResolvedTeachingProfile
```

The resolver returns the existing `ResolvedTeachingProfile` plus any missing explicit fields needed for testability:

- `include_intuition: bool`
- `include_assumptions: bool`
- `include_connections: bool`
- `max_examples: int`
- `response_opportunity_kind: Literal[...]`
- `local_override: TeachingOverride | None`
- `anchor_scope: Literal["lesson", "block", "selection", "branch"]`
- `visual_spec_kind: VisualSpecKind | None`
- `profile_version: str`

Use an enum rather than arbitrary strings for local overrides. This prevents a model prompt or browser label from becoming the state contract.

### 6.2 Plan compilation

`choose_teaching_plan` should compile the resolved profile into observable plan fields. It should not decide semantic behavior only in the model prompt.

Illustrative output:

```json
{
  "targetConceptId": "concept_derivative",
  "strategy": "direct_explanation",
  "teachingProfile": {
    "gear": "Deep",
    "depth": "mechanistic",
    "abstraction": "accessible",
    "stepSize": "fine",
    "derivation": "include",
    "exampleMode": "worked_with_boundaries",
    "localOverride": "simplify"
  },
  "representationSequence": [
    "plain_language_definition",
    "mechanism",
    "assumptions",
    "derivation",
    "worked_example",
    "boundary_case",
    "independent_response_opportunity"
  ],
  "intendedNextAction": "await_understanding_response"
}
```

The deterministic renderer and live model provider both consume this same plan. If a provider is unavailable, the deterministic renderer still demonstrates the control semantics in tests.

### 6.3 Structured output and provider boundary

The model provider is a wording/rendering capability. It may not change the plan’s objective, profile, or evidence decision.

Require structured lesson blocks with:

- block kind, heading, and Markdown body;
- concept IDs, source IDs, trust state, and `planId`;
- a `representation` value that maps to the plan sequence;
- for visuals, a validated `visualSpec` instead of executable SVG/HTML/JavaScript;
- for checks, `answerWithheld: true` and a private evaluator reference, never an answer in learner-visible text.

The existing provider prompt should add an explicit prohibition on silently omitting required plan representations. The server validates returned block kinds, block count, anchor compatibility, and visual/check metadata before delivery.

### 6.4 Visual-spec boundary

V1 visual output is data, not executable code.

```json
{
  "kind": "relationship_diagram",
  "title": "From average to instantaneous change",
  "nodes": [{"id":"a","label":"Average change"}],
  "edges": [{"from":"a","to":"b","label":"shrink interval"}],
  "textEquivalent": "As the interval becomes smaller, average change approaches the rate at one point."
}
```

Supported kinds initially: `relationship_diagram`, `comparison_table`, `number_line`, `worked_structure`, and `validated_plot`. The renderer rejects unknown types, oversized data, unsafe labels, invalid numeric values, and unsupported function domains. Fallback to a structured explanation or table rather than decorative imagery.

### 6.5 Action lifecycle, cancellation, and versions

Each UI action sends:

- `intent`;
- selected `gear` or null to inherit the session;
- optional `parentLessonId`, `parentBlockId`, and immutable anchor;
- `expectedStateVersion`;
- `Idempotency-Key` generated per logical user action;
- a client `supersedesActionId` for explicit replacement actions.

The server persists `action.started`, `profile.resolved`, `plan.created`, `plan.validated`, `artifact.created`, `verification.completed`, and either `lesson.completed`, `action.cancelled`, or `action.failed`.

Changing the session gear affects only new actions. “Apply to this explanation” is a new action linked to the older artifact. A new replacement cancels a prior pending replacement for the same anchor. The browser renders only a result whose action ID is still current for that target.

### 6.6 Learner state integration

Teaching Gear may influence planning but may not exaggerate knowledge:

- Opening, reading, regenerating, simplifying, visualizing, or closing a lesson records at most activity/exposure.
- A check creates no mastery update on display.
- A submitted check becomes evidence only after the evidence-admission service validates item status, assistance, answer evaluation, idempotency, and curriculum compatibility.
- “Example shown” and “answer revealed” must travel with later evidence as assistance metadata.
- The persisted action should reference the learner-state policy version and plan ID so later review can explain an adaptation.

## 7. API and web-client changes

### Required contracts

Extend existing contracts rather than fork them.

| Area | Change |
|---|---|
| `TeachingActionInput` | Add a typed `override`, optional `supersedesActionId`, and clearer anchor scope if not already represented by parent IDs. Keep `gear` nullable to inherit session preference. |
| `ResolvedTeachingProfile` | Add semantic boolean/enumerated fields described above and a version. |
| `TeachingPlan` | Persist the resolved profile, representation obligations, response requirements, limitation reasons, and anchor scope. |
| `LessonBlock` | Add a typed visual specification and check metadata; preserve existing JSON field naming. |
| `RunStatus` | Return profile, plan ID, action relationship/supersession state, and an honest trust/verification status. |
| Session API | Add a narrow update endpoint for saved session gear, protected by expected state version. |
| Web API client | Add types and helpers for profile, override, regeneration, cancellation, and plan inspection. |

### Suggested endpoints

```text
PATCH /v1/sessions/{sessionId}
  { "gear": "Guided", "expectedStateVersion": 4 }

POST /v1/sessions/{sessionId}/actions
  { "intent": "example", "gear": null,
    "parentLessonId": "lesson_…", "parentBlockId": "block_…",
    "override": "example", "expectedStateVersion": 5 }

POST /v1/sessions/{sessionId}/actions
  { "intent": "teach", "gear": "Deep",
    "parentLessonId": "lesson_…", "override": "apply_gear_to_lesson",
    "supersedesActionId": "run_…" }

POST /v1/actions/{actionId}/cancel
GET  /v1/teaching-plans/{planId}
```

Do not add an endpoint that lets the browser post a full `ResolvedTeachingProfile`; that would let a client bypass policy and makes future auth unsafe.

## 9. Acceptance criteria

The implementation is ready for review only when all of the following are true.

1. The first new session defaults to Guided; a changed gear persists for future session actions.
2. Quick, Guided, and Deep produce materially different `ResolvedTeachingProfile` and `TeachingPlan` values for the same objective and learner state.
3. Simpler changes abstraction and step size while retaining a Deep plan’s mechanism and derivation obligations.
4. Why?, Example, and Go deeper remain anchored to the selected claim/block and do not restart the entire lesson.
5. Visualize returns a validated, accessible visual spec or an explicit useful fallback.
6. Check understanding provides a question without its answer and does not change mastery merely because it was shown or read.
7. Repeated clicks/retries yield one logical artifact per idempotency key; canceled or stale results do not alter the newer response.
8. A user can see the active gear, local override, action status, and trust limitation without inspecting developer tools.
9. The deterministic backend tests prove behavior without an API key; live provider integration is optional and remains server-side.
10. Existing topic graph, session, material-reading, and sidecar flows continue to work.

## 11. Open decisions to make during implementation review

- Should “Go deeper” become its own explicit intent or remain a `why` action with an `expand_mechanism` override? The recommended V1 is the latter to avoid duplicate policy paths.
- Which two visual formats should ship first? The recommended V1 pair is `relationship_diagram` and `comparison_table`; add plots only after numeric validation is reliable.
- Should each session remember one gear globally or allow per-topic preference? The recommended V1 is one explicit session preference, copied into a new branch at creation.
- When is a local response inserted inline versus opened in the sidecar? The recommended rule: selected passage/Why?/Symbols open the sidecar; Example and Visualize may insert an inline, structured block when their anchor is the current latest response.

These are contained product decisions. They must not delay the core rule: the learner’s control must compile into a visible, validated teaching-plan difference.
